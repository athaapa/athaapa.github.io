Over the past week, I've been working on a small image convolution kernel in C++. The actual problem is pretty simple: apply a box blur to a grayscale image. I wasn't really interested in image processing itself, though. I wanted to learn more about performance engineering, specifically how to estimate theoretical limits, benchmark code, understand the generated assembly, and figure out why something is slow.

I also wanted to get more familiar with ARM SIMD, since I eventually want to apply what I learn here to [mohg](https://github.com/athaapa/mohg), my synthesizer.

I kept the scope pretty small: a single grayscale image, a box blur, direct convolution, and single-threaded execution on an M4 performance core.

The code is on [GitHub](https://github.com/athaapa/imgconv).

## Estimating the theoretical limit

Before optimizing anything, I wanted to get a rough idea of how fast the kernel could theoretically run.

I used one output pixel as the unit of work and assumed we'd be vectorizing across 4 output pixels at a time.

For a k×k kernel, each output pixel requires k² multiply-adds. NEON can process 4 floats per vector instruction, and the M4 has 4 NEON pipes, so the arithmetic throughput limit works out to:

$$
\frac{k^2}{16} \text{ cycles/pixel}
$$

For k=3, that's about 0.56 cycles/pixel.

Loads are another constraint. Each 4-wide float load handles one tap for 4 output pixels, so we need k²/4 loads per pixel. Assuming 3 loads/cycle, that gives:

$$
\frac{k^2}{12} \text{ cycles/pixel}
$$

For k=3, that's 0.75 cycles/pixel. Loads appear to be the limiting factor for every k.

At 4.4 GHz, that gives a theoretical limit of around **0.17 ns/pixel** for k=3.

This is obviously an optimistic estimate. It ignores a bunch of things, including loop overhead, address calculations, dependencies, and other instructions. Still, I wanted some number to compare against.

## Results

I benchmarked on a 741×488 grayscale image. These are kernel-only timings in ns/pixel.

| variant | change | k=3 | k=9 |
| --- | --- | --- | --- |
| `v0` | baseline, runtime k, nested vectors | 2.153 | 17.452 |
| `v1` | templated k | 1.939 | 6.342 |
| `v2` | flattened image | 1.654 | 6.015 |
| `v3` | converted image to floats beforehand | 1.578 | 5.495 |
| `v4` | inverted loops | 0.823 | 7.523 |
| `vImage` | Apple's `vImageConvolve_PlanarF` | 0.477 | 3.236 |
| theoretical limit | | 0.17 | 1.53 |

My fastest version for k=3 is still around 5x slower than the theoretical limit, and about 1.7x slower than Apple's vImage.

Interestingly, even vImage is about 2-3x slower than my estimated limit. So either the model is too optimistic, the limit is difficult to reach in practice, or both.

## Most of my predictions were wrong

This was probably the most useful part of the whole project. I had a rough idea of what each change would do before implementing it, but most of those predictions turned out to be pretty inaccurate.

### Vectorization

The first thing I tried was making k a template parameter, so the compiler would know the kernel size at compile time.

This helped a little, but the compiler still wasn't vectorizing the loop. I checked the vectorization remarks and found:

> cannot prove it is safe to reorder floating-point operations

So I tried compiling with `-ffast-math`.

I initially expected something like a 3-4x speedup, since a 4-wide vector instruction can do the work of 4 scalar instructions. In practice, I only got 1.13x for k=3 and 2.8x for k=9.

The problem with my prediction was that I was only considering the arithmetic. Even if the arithmetic becomes 4x cheaper, the rest of the instructions are still there.

I also found that the compiler was vectorizing across the kernel taps for a single output pixel. For k=3, that doesn't even fill all 4 lanes of a vector.

### Flattening the image

Originally, I stored the image as a `vector<vector<uint8_t>>`. I figured replacing it with a flat array wouldn't make much difference. The extra loads from the nested vectors seemed relatively insignificant compared to the convolution itself.

Turns out I was wrong. Flattening the image improved performance by about 1.29x for k=3.

I decided to look at the assembly and count the loads per output pixel. For k=3:

- `v1`: 22 loads/pixel
- `v2`: 17 loads/pixel

Assuming a throughput of 3 loads/cycle, that gives 7.3 and 5.6 cycles/pixel, respectively.

The predicted difference is about 1.7 cycles/pixel. The measured difference was 1.86 cycles/pixel.

I checked k=5 and k=7 as well, and the estimates were pretty close there too.

This was probably the first time I actually managed to predict a performance difference using a model of the hardware, rather than just guessing.

### Too many instructions

Next, I looked at the hardware performance counters for `v3`.

I measured an IPC of about 5.4, with roughly 36 instructions executed per output pixel.

An IPC that high suggested the CPU was doing a pretty good job keeping its execution units busy. The issue seemed to be that I was simply executing too many instructions.

My theoretical model only accounted for around 5-6 instructions per output pixel, whereas the actual implementation was executing 36.

One obvious problem was that I was only calculating one output pixel per iteration of the innermost loop.

### Inverting the loops

I decided to invert the loops so that the output pixels were innermost. Instead of calculating one output pixel by iterating over every kernel tap, I would iterate over each kernel tap and apply it across the output image.

This allowed the compiler to vectorize across output pixels instead.

For k=3, this gave me almost a 2x speedup over `v3`.

Unfortunately, performance got significantly worse as k increased. At k=9, `v4` was actually slower than `v3`.

I think the problem is memory traffic. With the loops inverted, each kernel tap requires another pass over the input image, along with reading and writing the output buffer.

Each float image is around 1.4 MB, so the working set is much larger than L1 cache. By k=9, we're making 81 passes over the image.

I haven't confirmed that this is the bottleneck with hardware counters yet, though. That's something I still want to investigate.

### What you benchmark matters

One other thing I noticed was how much the benchmark scope affected the results.

For k=3, `v4` was 2.62x faster than the baseline when I only measured the convolution kernel.

But when I included the allocations and the conversion from floats back to bytes, the end-to-end speedup dropped to 1.72x.

This makes sense in hindsight, but it's something I hadn't really considered when I started.

## Applying this to mohg

The main reason I started this project was to learn things I could eventually apply to my synthesizer.

One interesting parallel is that individual voices in a synthesizer are independent, much like output pixels in an image. It might make more sense to vectorize across voices rather than trying to vectorize the processing of a single voice.

I also want to be more conscious of memory access patterns. `v4` showed me that reducing instruction count isn't necessarily enough if the optimization introduces significantly more memory traffic.

More generally, I think the biggest thing I've learned is how to approach optimization. Instead of randomly changing code and checking whether it gets faster, I want to make predictions based on the generated instructions and the machine's throughput limits, then use benchmarks and hardware counters to see where my reasoning was wrong.

## What's next?

There are still a couple of things I want to figure out.

First, I want to confirm whether `v4` is actually limited by memory traffic. Looking at L1 misses and IPC for k=3 versus k=9 seems like a reasonable starting point.

Second, I'm curious what Apple's vImage implementation is doing differently. For k=3, it's still around 1.7x faster than my best version, and the gap gets larger for bigger kernels.

I don't think I'm particularly close to an optimal implementation yet, but that wasn't really the goal. I wanted to get better at understanding why code runs at the speed it does, and I think this was a useful first exercise.
